## Context and problem

Each edition is generated by a scheduled workflow that calls the Claude API (ADR-004) and has to reach the site with no recurring manual work. The file is uploaded by the project bot (a GitHub App) or by Filipe. The repository is public, so anyone can open a PR. An invalid file must not take the site down, and a published edition must be removable.

## Decision

**Format.** Markdown with YAML frontmatter, one file per edition, named `YYYY-MM-DD-resumo.md`, in `src/content/posts/`. The frontmatter carries `titulo`, `data`, `resumo`, `tags`, `status` (`publicado` or `retirado`), `motivoRetirada` (required when withdrawn) and the `artigos` list, each item with `titulo`, `fonte`, `url`, `publicadoEm`, `categoria` (`artigo`, `diretriz`, `alerta` or `noticia`), `tipo` and `acesso`. The list keeps the plan's name `artigos`, although it also carries guidelines, alerts and news (F2-01). Field names and values are identifiers and stay in Portuguese (AGENTS.md §2).

**Path.** A PR that GitHub's auto-merge merges once the required checks pass (Filipe's choice of 2026-11-27):

1. The generation workflow collects, generates and writes the `.md` file, and checks each item before any push; a failing item is dropped (ADR-004, F2-13).
2. The job pushes a branch, opens the PR with a GitHub App token created for the run and turns on GitHub's auto-merge for it. Filipe can also upload a file through "Upload files"; he merges that PR himself.
3. CI checks format, links, duplicates and names, and fails an App PR that touches anything outside `src/content/posts/`. These are the required checks of the `main` ruleset (F0-01, F1-01, F2-05).
4. GitHub merges the PR once every required check passes. No workflow merges, and none runs on `pull_request_target`.
5. Cloudflare Pages publishes.
6. If a check fails, the PR stays open, nothing is published and GitHub notifies Filipe (F2-09 tests that the notice arrives).

Until F2-05 exists, waiver W1 (`DECISIONS.md`) applies: Filipe dispatches the run, uploads the validated file and merges the PR after CI.

**Withdrawal.**

| Method | When to use it | Effect |
| --- | --- | --- |
| `status: retirado` (default) | An edition with an error or poor content | It disappears from the home page, the tags and the RSS; the URL shows "edição retirada" and the reason; its articles go onto the bot's block list |
| Delete the file | Content that must not stay visible on the site | The URL returns 404 |
| Revert the deploy in Cloudflare Pages | Emergency | Back to the previous version in seconds, without touching the repository |

## Alternatives considered

| Option | Pros | Cons | Why not (if rejected) |
| --- | --- | --- | --- |
| Markdown with frontmatter (chosen) | Readable and fixable by hand; a file in the folder is already a post | — | — |
| MDX | Components in the text | A stray `<` or `{` in AI text breaks the build | Rejected |
| JSON | Easy to validate | Hard to read and fix by hand | Rejected |
| `.docx` or PDF | Familiar | Needs conversion | Rejected |
| PR merged by GitHub's auto-merge once the required checks pass (chosen, 2026-11-27) | An invalid file stays parked in the PR; the site stays up; no merge workflow to write or secure; a PR from a fork cannot turn on auto-merge | The ruleset must name required checks, or auto-merge has nothing to wait for; availability on this repository unverified (F2-05) | — |
| PR merged by a custom auto-merge workflow (author allow list, path filter) | The workflow checks the author and the paths itself | A privileged workflow on pull requests, with the `pull_request_target` traps the 2026-11-26 review listed | Chosen until 2026-11-27; replaced by GitHub's auto-merge |
| Job commit to `main` with the Actions `GITHUB_TOKEN` | No private key; no PR workflow | A ruleset cannot exempt `GITHUB_TOKEN`, so `main` loses its "PR required" rule, and only `AGENTS.md` stops a mistaken push | Approved on 2026-11-26 (D9), replaced on 2026-11-27 |
| Job push to `main` with the App token, the App as the ruleset's only bypass | No PR per edition | CI does not check the file again before it lands; the same private key | Rejected on 2026-11-27 |
| Direct commit to `main` by hand | No code | An invalid file blocks every later deploy | Rejected |
| Upload page on the site | No GitHub needed for the uploader | A function, authentication and a secret to maintain | Deferred; F7-06, conditional |
| PR opened by a GitHub App (chosen) | Per-run token valid for one hour; scoped to this repository only; an author the path check can recognize; triggers PR validation | An App to create and a private key to keep | — |
| PR opened by the Actions `GITHUB_TOKEN` | No extra secret | The PR does not trigger the validation workflows | Rejected |
| Fine-grained personal token | Easy to create | Tied to Filipe's account; long validity; the PR author is Filipe | Fallback if the App does not work |

## Consequences

- Auto-merge waits on named required checks, which exist only once CI does: F0-01 creates the "PR required" rule, and F1-01 and F2-05 add the checks. A PR with a skipped or missing check does not merge (F2-05).
- A PR from a fork cannot turn on auto-merge, and the validation workflows run on `pull_request`, so it gets no secret.
- An App PR that touches a path outside `src/content/posts/` fails a required check.
- Validation runs on the PR, outside the build. Only valid files reach `main`.
- With the repository public, withdrawn or deleted text stays in the Git history.
- The bot is a GitHub App installed only on this repository, with access only to contents and pull requests (F2-05). The token is created on each run and lasts one hour; the stored secret is the App's private key, which only the generation job can read.
- The PR must be opened by the App, not by the Actions `GITHUB_TOKEN`: a PR opened with the `GITHUB_TOKEN` does not trigger the PR validation workflows.
- The App's private key stays, although D9 of 2026-11-26 meant to remove it; in exchange, `main` takes only PRs whose checks passed.

## Evidence

None yet for the path itself. On 2026-11-25 the Grok routine was replaced by generation through the Claude API (ADR-004), and F0-02 was withdrawn.

On 2026-11-26 the plan review approved a job commit with `GITHUB_TOKEN` (D9 in [`docs/plan-review-2026-11-26.md`](../plan-review-2026-11-26.md)). While planning F0-09, GitHub's docs ("Creating rulesets for a repository") showed that a ruleset's bypass list takes only repository roles, teams, GitHub Apps and Dependabot, not `GITHUB_TOKEN`, so that commit could not pass the "PR required" rule. On 2026-11-27 Filipe chose the App PR with GitHub's auto-merge.

The state stays `proposed` until F2-09 publishes a real file through the flow.

## Review when

- F2-05 shows that the GitHub App or GitHub's auto-merge does not work on this repository. The fallbacks: a fine-grained personal token with an expiry, which makes Filipe the PR author, or Filipe merging by hand as under W1.
- Manual upload becomes a nuisance after two weeks of operation (F7-06).
- Phase 9 starts: auto-merge then requires an approval (F9-01).
